# StrataWP and headless WordPress

Research for [#62](https://github.com/JonImmsWordpressDev/strataWP/issues/62), November 2026.

The question: how well does StrataWP work as the base for a headless WordPress site, and what would make it a strong choice? The use case to judge against is a large marketing site: hundreds to thousands of pages, several content editors, landing pages built from blocks, strong SEO needs, WordPress as the CMS and a separate frontend such as Next.js or Astro.

Short answer: **partly**. StrataWP is a good WordPress-side toolkit for the editing experience (typed custom blocks, theme.json, patterns), and it ships a small REST client (`@stratawp/headless`). But almost everything that makes it valuable today is aimed at WordPress rendering the page itself, and the pieces a decoupled frontend needs most (block data, design tokens, preview, revalidation, menus, SEO data) are either missing or thin. Details below.

## 1. Headless options today

| Approach                                  | What the frontend gets                                                                                       | Strengths                                                                                                                                                            | Weaknesses                                                                                                                                                                               |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **WP REST API (core)**                    | `/wp/v2/*` JSON: posts, pages, CPTs with `show_in_rest`, media, terms. `content.rendered` is the final HTML. | Built in, no plugin, cache-friendly GETs, well documented.                                                                                                           | Over-fetching and many round trips (`_embed` helps a little). No block tree in the public response. Menus, global styles and drafts need authentication.                                 |
| **WPGraphQL**                             | One typed GraphQL schema over posts, pages, CPTs, menus, media, settings.                                    | One request per page, typed queries, a large extension ecosystem (ACF, SEO plugins, Polylang/WPML). Becoming a WordPress.org canonical plugin, backed by Automattic. | A plugin to run and keep updated. Query cost needs watching on big sites. Caching is harder than plain GETs (persisted queries or a CDN layer help).                                     |
| **Block data (WPGraphQL Content Blocks)** | `editorBlocks` on each post: block name, attributes, inner blocks as data.                                   | The frontend renders each block as its own component (true design ownership, no theme CSS needed).                                                                   | Every block, core and custom, needs a frontend component. Core block coverage and attribute fidelity vary. Extra plugin.                                                                 |
| **Faust.js (WP Engine)**                  | Next.js framework on top of WPGraphQL: template hierarchy, preview, auth, `@faustwp/blocks` renderer.        | Solves preview and routing out of the box.                                                                                                                           | Opinionated, Next.js only, tied to WPGraphQL plus the FaustWP plugin. Ecosystem pace is set by one host.                                                                                 |
| **Render `content.rendered` HTML**        | Server-rendered HTML for each post, dynamic blocks included.                                                 | Every block "just works", editors see what they built. Fastest path.                                                                                                 | The frontend must load the theme's block CSS and the WordPress block-library CSS, so design stays coupled to the theme. Hard to swap individual blocks for interactive React components. |
| **Parsed block JSON**                     | `parse_blocks()` output, via a custom REST field or Content Blocks.                                          | Fine-grained control, clean data for SEO and structured data.                                                                                                        | You maintain a component per block, plus a fallback for unknown ones (usually: render the block's HTML).                                                                                 |

In practice, large marketing sites usually land on a **hybrid**: parse blocks into data, map the high-value blocks (hero, CTA, feature grids, forms) to frontend components, and fall back to the block's rendered HTML for everything else. That keeps editors free to use core blocks without a component for each.

Sources:

- WordPress REST API handbook: https://developer.wordpress.org/rest-api/
- WPGraphQL becoming a canonical plugin (WordPress.org news, October 2024): https://wordpress.org/news/2024/10/wpgraphql/ and the plugin page https://wordpress.org/plugins/wp-graphql/
- WPGraphQL Content Blocks: https://github.com/wpengine/wp-graphql-content-blocks
- Faust.js and `@faustwp/blocks`: https://wordpress.org/plugins/faustwp/ and https://www.npmjs.com/package/@faustwp/blocks
- Next.js draft mode (App Router): https://nextjs.org/docs/app/guides/draft-mode

## 2. StrataWP audit

Legend: **as-is** (works headless today), **with changes** (useful headless after work), **theme only** (only matters when WordPress renders the frontend).

A note that shapes everything below: in a headless setup the StrataWP theme still has to be **active on the CMS**. That is where custom blocks are registered (`inc/blocks-generated.php`, loaded by the core `Blocks` component), where theme.json drives the editor, and where patterns live. So "theme only" does not mean useless: it means it helps editors, not the frontend.

### packages/core (PHP components)

| Feature                                                                                        | Verdict                                                  | How a frontend would get at it                                                                                                                                                                                                                     |
| ---------------------------------------------------------------------------------------------- | -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Theme` class, component pattern, `stratawp_theme_components` filter                           | **as-is**                                                | Not consumed by the frontend, but it is the natural home for a future `Headless` component (REST fields, preview links, revalidation webhooks).                                                                                                    |
| `Blocks` (registers auto-generated custom blocks)                                              | **as-is** for editing, **with changes** for the frontend | Blocks are registered, so editors can use them, and dynamic blocks appear rendered in `content.rendered`. Their attributes are only in the raw block comments, which public REST does not return. Needs a block-data REST field or Content Blocks. |
| `Setup` (theme supports, custom logo, content width)                                           | **theme only**                                           | Logo and site settings are reachable via `/wp/v2/settings` with auth only.                                                                                                                                                                         |
| `Assets` (manifest-based enqueue)                                                              | **theme only**                                           | Enqueue happens on WordPress pages. The frontend would need the built block CSS copied or published separately.                                                                                                                                    |
| `ConditionalStyles`, `CriticalCss`, `Performance` (resource hints, async/defer, bloat removal) | **theme only**                                           | Frontend frameworks handle this themselves.                                                                                                                                                                                                        |
| `Accessibility` (skip-link fix, `aria-current`, screen-reader CSS)                             | **theme only**                                           | The frontend must reimplement these.                                                                                                                                                                                                               |
| `ImageSizes` (`sizes` tuning, `<picture>` sources)                                             | **with changes**                                         | `/wp/v2/media` already returns every registered size, and `@stratawp/headless` has `getImageSrcSet` and `getNextImageProps`. The `sizes` rules live in PHP filters and would need to be shared as data.                                            |
| `Fonts` (font pairings, CSS variables printed in `wp_head`)                                    | **with changes**                                         | The variables are only printed on WordPress pages. Expose as tokens (see gap 1).                                                                                                                                                                   |
| `Icons` (icon font and template tags)                                                          | **with changes**                                         | The icon CSS file can be served to the frontend as a static asset. Template tags are PHP only.                                                                                                                                                     |
| `Analytics` (dev-cookie exclusion)                                                             | **theme only**                                           | Analytics would move to the frontend.                                                                                                                                                                                                              |
| `Updates` (GitHub theme updates)                                                               | **as-is**                                                | Keeps the CMS theme updated. Unaffected by headless.                                                                                                                                                                                               |

### Example themes and the vite plugin

| Feature                                                                                                             | Verdict                         | How a frontend would get at it                                                                                                                                                                     |
| ------------------------------------------------------------------------------------------------------------------- | ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| theme.json (palette, spacing, typography, custom templates)                                                         | **with changes**                | Core's global-styles REST route needs `edit_theme_options`. There is no public JSON or CSS-variable export. Today the frontend would copy values by hand and drift.                                |
| Custom blocks (`hero`, `feature-card`, `portfolio-grid`, `team-members`, `featured-products`, `product-categories`) | **with changes**                | All are dynamic (`render.php`), so their HTML appears in `content.rendered` with theme class names. To render them as frontend components the frontend needs their attributes (see gap 3).         |
| `block-attributes.ts` codegen from block.json (`vite-plugin/src/plugins/block-types.ts`)                            | **with changes**, high leverage | Already produces typed attribute interfaces per block. The same types could be published for frontend block components, so editor and frontend stay in lockstep.                                   |
| Patterns (70+ PHP patterns in `patterns/`)                                                                          | **as-is** for editors           | Patterns just insert blocks, so whatever they produce goes through the block data path.                                                                                                            |
| Templates and parts (`templates/*.html`, `parts/*.html`)                                                            | **theme only**                  | The frontend owns routing and layout. Site Editor template changes do not reach it.                                                                                                                |
| Menus (`register_nav_menus` in `inc/Components/Navigation.php`)                                                     | **with changes**                | Core `/wp/v2/menus` and `/wp/v2/menu-items` require authentication by default, so a public frontend needs a server-side token, WPGraphQL menus, or a small public endpoint for assigned locations. |
| Companion CPTs (`plugins/strata-advanced-content`)                                                                  | **as-is**                       | Registered with `show_in_rest: true`, so they are readable via REST today through the client's generic `get()`.                                                                                    |
| Image optimization (sharp, AVIF/WebP siblings)                                                                      | **theme only**                  | Applies to theme assets, not Media Library uploads.                                                                                                                                                |
| PHP HMR, block auto-registration, manifest                                                                          | **as-is** for theme dev         | Still useful for developing the CMS-side blocks. No frontend role.                                                                                                                                 |

### packages/headless

| Feature                                                              | Verdict                     | Notes                                                                                                                                                                                                                                                                                                                                                |
| -------------------------------------------------------------------- | --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `WordPressClient` (posts, pages, terms, users, media, generic `get`) | **as-is**                   | REST only. No GraphQL despite the package keywords. Typed for core fields only. CPTs work through `get()` without types.                                                                                                                                                                                                                             |
| Auth (basic, application password, JWT, OAuth headers)               | **as-is, server side only** | Credentials are set on the client instance. Using an authed client from the React hooks in the browser would ship the credentials to visitors, and the docs do not warn about this.                                                                                                                                                                  |
| React hooks (SWR)                                                    | **as-is**                   | Client-side fetching. A marketing site would mostly fetch on the server instead.                                                                                                                                                                                                                                                                     |
| Next.js helpers (`getAllPosts`, `generatePostParams`)                | **as-is**, with limits      | Paginate 100 at a time. Fine for hundreds of pages. For thousands, a sitemap-driven or incremental approach is better than fetching every post at build time.                                                                                                                                                                                        |
| `revalidateTag` / `revalidatePath`                                   | **with changes**            | They load `next/cache` with `require()` inside an ESM-only package (`tsup` builds `format: ['esm']`). If Node loads the package as native ESM rather than through the bundler, `require` is undefined and the call fails into the `catch`, which only logs. Worth a test in a real Next.js app. Nothing on the WordPress side calls them on publish. |
| Preview (`isPreview`, `getPreviewData`, `enablePreview`)             | **with changes**            | Reads the Pages Router `__next_preview_data` cookie. App Router draft mode uses `draftMode()` and the `__prerender_bypass` cookie, so `isPreview` returns false there. `verifyPreviewSecret` uses `===`, not a constant-time compare. Nothing on the WordPress side points the "Preview" button at the frontend.                                     |
| SEO helpers (`generatePostSEO`, `extractExcerpt`)                    | **with changes**            | Build metadata from title and excerpt. They do not read SEO plugin output (StrataWP SEO, Yoast, Rank Math), which is where editors actually set titles, descriptions, canonicals and schema.                                                                                                                                                         |
| Tests                                                                | missing                     | The package has no tests, unlike most of the monorepo.                                                                                                                                                                                                                                                                                               |

### CLI and create-stratawp

| Feature                                                  | Verdict                     | Notes                                                                          |
| -------------------------------------------------------- | --------------------------- | ------------------------------------------------------------------------------ |
| `block:new`, `component:new`, `template:new`, `part:new` | **as-is** for CMS-side work | Block scaffolds generate `render.php` for WordPress, not a frontend component. |
| `deploy`, `sync:db`, `sync:templates`, `rollback`        | **as-is** for the CMS       | Useful for running the WordPress side. No frontend deploy.                     |
| `create-stratawp` templates (basic, advanced, store)     | **theme only**              | No headless template or frontend starter.                                      |

## 3. Verdict

**Partly.** StrataWP is a solid choice for the WordPress side of a headless build: typed custom blocks, a disciplined theme.json, patterns for editors, CPTs in a companion plugin, and deploy and sync tooling for the CMS. It is not yet a headless framework. Its frontend story is a thin REST client whose preview and revalidation helpers target older Next.js conventions, there is no way to get block data or design tokens out to the frontend, nothing on the WordPress side wires preview links or publish webhooks to the frontend, and it has no reference frontend. For a large marketing site today you would pair StrataWP's CMS side with WPGraphQL (plus Content Blocks) and your own Next.js or Astro app, and `@stratawp/headless` would play a small role. Closing gaps 1 to 4 below would make "StrataWP for headless" a credible pitch rather than a partial one.

## 4. Gap list

Ranked by value for the use case above. Sizes: small (a day or less), medium (a few days), large (a week or more).

1. **Design tokens export.** Have the vite plugin emit `dist/tokens.json` and `dist/tokens.css` (CSS custom properties) from theme.json at build: palette, font families and sizes, spacing, layout widths. The frontend imports the same tokens the editor uses, so the brand cannot drift between the two. **Small to medium.**
2. **Block data in REST, with typed attributes.** A core `Headless` component that adds a `blocks` field to posts, pages and REST-enabled CPTs: the parsed block tree (name, attributes, inner blocks), plus each block's rendered HTML as the fallback. Publish the generated `block-attributes.ts` types so frontend block components share the editor's types. This is what lets a frontend render a StrataWP hero as a real component. **Medium.**
3. **Preview and revalidation, end to end.** WordPress side: filter `preview_post_link` to the frontend's draft route with a signed token, and send a signed webhook to a configurable frontend URL on publish, update and trash (`transition_post_status`, `save_post`), carrying post type, id and path. Frontend side: App Router `draftMode()` support, an ESM-safe import of `next/cache`, and a constant-time secret check in `@stratawp/headless`. **Medium.**
4. **Reference frontend starter.** A minimal Next.js App Router app (or `create-stratawp --headless`) with token import, a block renderer that maps StrataWP blocks to components and falls back to HTML, preview, revalidation, sitemap and SEO metadata. This is what turns the pieces into something a team can evaluate in an afternoon. **Large.**
5. **SEO data from the CMS.** Read the active SEO plugin's per-post output (title, description, canonical, robots, Open Graph, JSON-LD) over REST or GraphQL, and have `generatePostSEO` prefer it over title and excerpt. For the StrataWP SEO plugin, a REST field it registers itself. **Medium.**
6. **Public menus.** A read-only endpoint (or documented WPGraphQL setup) for menus assigned to theme locations, so the frontend can build header and footer navigation without an admin token. **Small.**
7. **Block CSS for the HTML fallback.** Publish the built block styles (per-block CSS from `dist/`) as a stable URL or package, so fallback HTML from dynamic blocks renders correctly on the frontend. **Small.**
8. **Tests and hardening for `@stratawp/headless`.** Unit tests for the client, pagination and helpers, plus a docs warning that authenticated clients are server-only. **Small.**

Items 1 to 3 are filed as `agent-proposed` issues for approval. GraphQL support in `@stratawp/headless` is deliberately not on the list: if a project wants GraphQL, WPGraphQL plus its client tooling is a better bet than a second StrataWP client.
